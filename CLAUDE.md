# Alvik

Arduino Alvik robot (MicroPython, ESP32) for the kids, plus a web remote. Backlog = GitHub issues on `gabeduke/alvik`. Setup and commands: README.md.
The repo and the site are public and written for strangers too: a visitor may have no robot (pretend robot), or a robot and no terminal (flash page, lessons).

## Layout
- `src/` – core robot files (`main.py` → `demo.py` colour menu; `remote_control.py` = purple "phone remote"; `dance.py` = shared disco dance; `sketchbook.py` = finds sketches).
- `sketches/<name>/` – extra menu programs: `<entry>.py` with `run(alvik)` (called until ✗; negative return = back to menu), `sketch.json` (title, emoji, description, color [r,g,b] 0/1, hardware, entry), `README.md`. On the robot: `/sketches/<name>/`, found at boot by listing the folder (no index on the robot). Menu = 4 built-ins then sketches sorted by name; pages of 6, page N blinks N-1 times per 2 s; crashes flash red and return. How to add one: README "Sketches".
- `docs/` – the web remote (installable PWA: `manifest.webmanifest`, `sw.js`, `pwa.js` = SW registration + update toast with a busy hook), deployed by `.github/workflows/pages.yml` (Pages source = GitHub Actions) at https://gabeduke.github.io/alvik/. Push to `main` = deploy (~1 min). Pages sends `cache-control: max-age=600`. Served under `/alvik/`: use relative URLs. New pages go in `SHELL` in `sw.js`.
- 3D twin on the remote: `docs/twin.js` (three.js viewer, loaded lazily; the remote must keep working without it; how a reading becomes a colour, a height or a heading is plain maths in `docs/sensing.js`, tested without WebGL) shows `docs/models/alvik.glb` (metres, faces +Z, left = +X; parts `Body`, `Baseplate`, `WheelL`/`WheelR`, `LedL`/`LedR`, `Tof`). Rebuild the model with `/Applications/Blender.app/Contents/MacOS/Blender -b --python models/build_alvik_web.py` (sources and licences: `models/README.md`; the baseplate is CC BY-NC-SA, keep the credit on the page and in the GLB). three.js 0.170 is vendored in `docs/vendor/three/`; the import map in `index.html` maps `three` to it.
- Printable Grove holders (LEGO brick underneath, tray for a 20x20 or 20x40 Grove board on top, snap-on lids for the Speech Recognizer and the Speaker): `models/build_grove_holders.py` builds `models/grove/*.stl` (mm); numbers, print notes and what is still unproven are in `models/grove/README.md`. The Alvik's Grove ports are I2C at 3.3 V only.
- Pretend robot ("try it without a robot", `?demo` or the button): `docs/pretend.js` (plain sums, no DOM: the room `ROOM`, made-up sensor readings, and the robot's side of the packets) run by `docs/playroom.js` (timer + the little map). It stands where the Bluetooth characteristic would (`rx`), so `index.html` treats it like a robot. Its ramp and bumper are `docs/bumper.js`, a JavaScript copy of `ramp`, `bumper_limit`, `Zone`, `Bumper` from `remote_control.py`: change them together, then `WRITE_VECTORS=1 python3 tests/test_robot.py SharedSums` rewrites `tests/bumper_vectors.json`, which both sides are tested against.
- Site navigation: every page has the same bottom tab bar (`nav.tabbar`, styles in `docs/app.css`): Drive, Lessons, Set up (flash page), About (`./#about` opens the dialog). On the remote it hides while a real robot is connected. The remote's header is name, status, layout switch, Connect; not connected shows `#start` (how to get the robot ready); the pretend robot shows `#demoBar` (purple, with its own Stop), and Connect then means "a real robot instead".
- New visitors: `<dialog id="about">` opens by itself the first time a device comes (no `alvik-layout` in localStorage) and from ❓ About; the "No robot?" button (`#tryDemo`, in `#start`) shows only on a guest device: one whose first visit set `alvik-guest`, until it connects to a real robot. A device that was already a remote before is never a guest, and the tab bar hides while a real robot is connected. Don't put anything in the way of a device that already drives a robot. Pretend and real never run together (`taken()`).
- Lessons: `docs/learn/` (nine hand-written pages + `index.html` + `learn.css`; small widgets are inline module scripts that import `../bumper.js`). They link to the remote with `?show=` (comma list of `cloud`, `heat`, `under`; twin `show()`) so sensors come online one lesson at a time. `tests/learn.test.mjs` checks their links, that they are in `SHELL`, and that the numbers and code they quote still match `src/` (it names what to update); `pretend.test.mjs` does the same for the numbers `pretend.js` and `bumper.js` copy from the robot. Lesson 8's worked example is the real sketch `sketches/scaredy_cat`.
- `scripts/build_site.sh` builds `_site/` = `docs/` + `robot/` (`src/*.py` + `index.json` with path/size/sha256) + `sketches/<name>/` (+ per-sketch `index.json`) + `sketches/index.json` (validated by `scripts/sketch_index.py`), and stamps the commit into `sw.js`. `OUT=dir` builds elsewhere.
- `docs/flash.html` + `docs/flasher.js`: Web Serial flasher (raw REPL like mpremote). Reuse `loadBundle(url)`, `loadSketchFiles(site, name)` (core + sketch, robot paths) + `flashFiles(transport, files, {onEvent})`. A sketch flash always includes all core files.
- Tests: `node --test tests/*.test.mjs` (fake board: `tests/fake_repl.mjs`; `twin.test.mjs` checks the GLB's part names and that `SHELL` files exist; `sensing.test.mjs` the twin's maths; `pretend.test.mjs` the pretend robot; `learn.test.mjs` the lessons) and `python3 tests/test_robot.py` (menu + sketches on a fake Alvik with a virtual clock). Both run in the Pages workflow. Keep robot code MicroPython-safe (no `os.path`/`pathlib`; `except Exception` must not swallow KeyboardInterrupt, the flasher's Ctrl-C).

## Robot over USB
- `.venv/bin/mpremote` (venv from README). Port is usually `/dev/cu.usbmodem1234561`; it disappears when the robot is unplugged.
- Only one program can hold the port: close Arduino Lab for MicroPython first.
- Deploy: `.venv/bin/mpremote fs cp src/*.py : + reset`, or the 🔧 flash page in Chrome (flashes what's on `main`). Smoke test: `mpremote exec "import remote_control" + reset`. Install a sketch by hand: `mpremote fs mkdir :sketches` (once), then `mpremote fs cp -r sketches/disco :sketches/ + reset`.
- Any mpremote command interrupts the running menu; finish with `+ reset`.
- Alvik library is in `:lib/arduino_alvik` (reinstall: `mpremote mip install github:arduino/arduino-alvik-mpy`).

## Bluetooth protocol (remote mode)
- Nordic UART service `6E400001-…`, robot advertises as `Alvik`. Phone writes to RX `6E400002-…`.
- Bluefruit Connect Control Pad packets: `'!' 'B' <'1'..'8'> <'1' down | '0' up> <checksum = ~sum(first 4) & 0xFF>`.
- Buttons: 1 lights, 2 turbo (toggle), 3 disco dance, 4 bumper (toggle, on by default), 5 up, 6 down, 7 left, 8 right. Arrows are hold-to-drive (Bluefruit app only; the web remote drives with the joystick).
- Web remote drive layouts (`body[data-layout]`, saved in localStorage `alvik-layout`): `stick`, `two` (throttle + steer sliders). Both feed one (x, y) and the same packet.
- Web remote joystick packet: `'!' 'J' <x int8> <y int8> <checksum>`, -100..100, x right, y forward. The page repeats it every 150 ms while held; the robot stops after 600 ms of silence. Speeds ramp (`ramp()`), and the bumper slows from 14 cm and stops at 8 cm (`bumper_limit()`).
- The distance sensor is noisy and sees the floor: with nothing ahead its front zones read 16-18 cm on the real robot (a wall behind that spot reflects more and is read instead), and a zone that mostly reads something far drops to the floor's reading for a few readings at a time. So the bumper never uses raw `get_distance()`. `SLOW_CM` stays under where the floor shows, so the floor is never a thing. `Bumper.look()` in `remote_control.py` gives one distance: the second-closest of the middle three zones, so two zones must agree (a stray reflection in one zone, e.g. on a shiny kitchen table, does nothing). Each zone first goes through `Zone.see()`, which drops blips (a thing must show in `SURE` new readings in a row; the real sensor makes a new set only every 1-9 loop trips and repeats it in between, so `Bumper.look()` only feeds the zones when the five readings change, and the fake robot in `test_robot.py` and `pretend.js` do the same) and learns a nose-down floor (a "thing" that comes no closer over `FLOOR_PROOF_CM` of driving is ignored until the zone sees past `SLOW_CM` again). Consequence: something narrow in one zone (a chair leg) is not seen. To re-measure: robot on open floor, `get_distance()` over USB.
- Telemetry (robot → page, NUS TX `6E400003-…` notify), sent every `TELEMETRY_MS` = 100 ms (about 8 a second with the 30 ms loop; all three packets take about 3 ms to build on the robot) only after the page sends `'!' 'T' '1' <0> <checksum>` (off again on disconnect): `'!' 'T' <heading int16 LE, 0.1°, left +> <front cm = what the bumper acts on (`Bumper.look()`), 255 = none> <lights: bits 0-2 left RGB, 3-5 right> <speed int8, 0.2 cm/s> <turn int8, 3°/s, left +> <flags: 1 turbo, 2 bumper, 4 blocked, 8 dancing> <checksum>`. Built by `telemetry_packet()` in `remote_control.py`, read by `docs/telemetry.js`; both are tested against `tests/telemetry_vectors.json`, so change all three together. Heading is `get_pose()` theta (odometry). Right after it comes a sensors packet, `'!' 'S' <5 raw distances cm left→right, 255 = none> <roll int8 °> <pitch int8 °> <battery %, 255 = unknown> <checksum>` (`sensor_packet()`), then what is under the robot, `'!' 'U' <3 line sensors left→right, raw / 4, dark = high, 255 = unknown> <floor red> <green> <blue, each 0..100 as `get_color()` normalises it, 255 = unknown> <bottom cm> <top cm, 255 = none> <checksum>` (`under_packet()`), same shared examples. New sensor data: add a new packet letter rather than changing these (old pages skip letters they don't know; the page must cope with robot code that doesn't send it).
- Twin, what it draws from that: a point cloud of every raw reading (`S` zones plus `U` top and bottom, fading after `CLOUD_MS`), a heat sheet across the middle three zones at the `T` distance, so it shows only what the bumper acts on (`heatAt()`: yellow from `SLOW_CM`, red from `BUMPER_CM`, imported from `bumper.js`; `VIEW_CM` = 30 is only the picture's scale), a floor patch in the sensed colour, three line-sensor dots at the nose, and it rises with the bottom distance (`liftOf()`; `FLOOR_CM` = 7.4 is the real robot's reading standing on a desk). `LINE_PALE`/`LINE_DARK` and the lift scale in `sensing.js` are guesses until read off the real robot (#11). Heading is predicted a little ahead (`compassNews()`).
- Web remote layout: `main` is a CSS grid with areas `w` (3D twin, takes the spare room), `k` (joystick) or `t`/`s` (sliders), `a` (the four-button dock); the areas are rearranged per layout and orientation in one block of `index.html`.
- **One connection at a time.** While anything is connected the robot stops advertising, so the web page can't see it until the Bluefruit app disconnects (lights go yellow = advertising).
- Web Bluetooth: Chrome/Edge on Android, macOS, Windows. Not iPad/iOS Safari (use the Bluefy app). macOS needs Chrome allowed under Privacy & Security → Bluetooth.

## Conventions
- Words for readers (pages, lessons, README): plain and short, for a grown-up and a child; say "pretend robot", not simulator. Only claim what the code or the real robot has shown; `docs/img/share.png` is the share picture (a 1200x630 screenshot of `?demo`).
- Kid-facing: big buttons, emoji labels, robot lights as feedback (yellow = waiting; bumper: slow red blink = slowing, fast red flash = stopped).
- The web remote is static files with no bundler and no install step (the build script only copies and indexes). The one library is three.js, vendored as plain files in `docs/vendor/` (see its README to update). Don't add others unless an issue says so.
